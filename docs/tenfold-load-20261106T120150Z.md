# Five-minute 10× arrival-rate test — 2026-11-06

The requested 10× test was interpreted as **25,000 requests/sec**, versus the
previous 2,500/sec baseline. The optimized FST/Hyper server survived under the
same 8 MiB charged-memory / half-core CPU ceilings, but **failed the load target**.
No application code, resource ceiling or validation check was changed for this run.

Correct responses were 11.71% of the 7.5 million intended arrivals. Zero response
errors does not compensate for dropped arrivals. The script exited with k6
threshold status 99, and `completed` is false. The test ran for the full arrival
period; that flag indicates failed acceptance gates, not an early interruption.

Settings: one server worker, 200 preallocated/max VUs, 2,000 rotating device
labels, 178,507 rules, 12,000 preflight cases, loopback HTTP, no swap. The kernel
limits were verified as `cpu.max=5000 10000`, `memory.max=8388608`, and
`memory.swap.max=0`. Temporary server services were cleaned up after testing.

The executable, index, cases and k6 script hashes exactly match the earlier
[five-minute 2,500/sec run](benchmarks/dataflow-sustained.json), which handled 2,481.72/sec
and also failed its gates. CPU frequency and competing desktop work were not
controlled. The starting frequency snapshot was approximately 800 MHz across
the logical CPUs. This is a workload comparison, not isolated server capacity.

The cgroup recorded only 394 additional throttled periods after startup,
totaling 0.332483 seconds of throttled time. The generator consumed much more
CPU than the target. These observations suggest substantial generator/host
limitations, but do not prove which component caps end-to-end throughput. A
separate load host is needed to qualify server capacity independently.

Resource sampling covered 313.32 seconds, including setup, drain and final k6
summary work. RSS includes the server and index; cgroup accounting differs
from RSS. The one memory-limit event and cleanup peaks are retained. The
handled/configured-second figure can include responses completed during drain.
This is an HTTP matcher harness, not a DNS transport benchmark or evidence for
2,000 simultaneous DNS clients.
